# 수강 신청 시스템 
## 프로젝트 개요
### 프로젝트 설명
- 강사는 강의를 등록하고 수강생은 수강 신청 및 결제를 할 수 있는 수강 신청 시스템입니다.
### 문서화
- 요구사항 분석, 객체 정의, 유스케이스 분석, API 명세서, ERD 문서 작성 후, 개발을 진행했습니다.
### 동시성 제어
- 동시 신청 상황에서 정원이 초과되지 않도록 동시성 제어 로직을 구현했습니다.
### 계층 간 역할 분리 
- 검증 로직은 도메인에 흐름 조율은 서비스로 나눔으로써 계층 간 역할을 분리하려고 노력했습니다.

## 설계 결정과 이유
### 동시성 제어 - 비관적 락
**[정원 관리]**
- 수강 신청 시 정원 관리에 대한 동시성 문제는 아래와 같은 이유로 비관적 락을 사용하여 해결하게 되었습니다.
- 수강 신청 시스템 특성상 요청이 늘어나면 병렬 확장을 우선적으로 고려하게 될 것이고, 이 때 애플리케이션 락을 사용하면 동시성 문제를 해결할 수 없습니다.
- Redis 분산락의 경우는 현재 시스템 규모에서는 추가 인프라 비용과 운영 복잡도에 비해 이점이 크지 않다고 판단하여, 데이터 정합성을 함께 보장할 수 있는 DB 비관적 락을 사용했습니다.
- 정원 관리의 경우 여러 사용자가 동시 요청을 통해 충돌이 자주 발생합니다. 그렇기에 낙관락을 사용하기 보다는 확실하게 충돌을 보장할 수 있는 비관적 락을 사용하는게 더 효율적이라고 생각했습니다.


**[강의 상태 변경]**
- 강의 상태 변경 시 동시에 여러 요청이 들어올 경우, 이미 상태가 변경된 강의에 대해 중복으로 상태 변경이 발생할 수 있습니다.
- 이를 방지하기 위해 조건부 `UPDATE(WHERE status = 'DRAFT' AND id = ?)`를 사용했습니다.
- 업데이트된 행이 0건이면 이미 처리된 요청으로 판단하여 409를 반환합니다.
- 이 방식은 별도의 락 없이도 DB 레벨에서 원자적으로 상태 변경을 보장합니다.


### QueryDSL 사용
- JPQL은 문자열 기반이기 때문에 쿼리를 잘못 작성할 경우 컴파일 시점에 오류를 잡을 수 없습니다.
- QueryDSL은 컴파일 시점에 이를 감지하므로 런타임 오류를 줄일 수 있습니다.
- JPQL은 동적 쿼리가 불가능하지만, QueryDSL을 사용하면 쉽게 동적 쿼리를 작성할 수 있습니다.


### N + 1 문제 해결 
**[강의 목록 조회]**
- 강의 목록 조회는 강사 이름을 함께 표시해야 하므로 User와 Course 정보가 모두 필요합니다.
- LAZY 로딩 상태에서 강사 이름을 가져오면 Course마다 User 조회 쿼리가 추가적으로 발생하여 N + 1 문제가 발생합니다.
- 이를 해결하기 위해 Course 목록을 먼저 조회한 뒤, instructorId를 추출하여 IN 쿼리로 User를 일괄 조회하는 방식을 선택했습니다.
- 다만 조회하는 강의 개수가 많아져 IN 절에 들어가는 ID 개수가 많아지면 쿼리 성능이 저하될 수 있으므로, 페이지네이션을 적용하여 한 번에 조회하는 강의 수를 제한하고 IN 절 크기를 제어하고 했습니다.


**[강의별 수강생 목록]**
- 수강생 목록의 경우 조회할 때마다 Enrollment와 User 정보가 모두 필요합니다.
- LAZY 로딩 상태에서 수강생 정보를 가져오면 Enrollment마다 User 조회 쿼리가 추가적으로 발생하여 N + 1 문제가 발생합니다.
- Enrollment와 User 사이에 연관관계가 있고, 가져올 Enrollment의 크기가 예측 가능하므로 Fetch Join을 사용하여 하나의 쿼리로 함께 조회했습니다.
- 즉, Course에 정원 제한이 있으므로 가져올 Enrollment 크기를 예측할 수 있어 Fetch Join으로 하나의 쿼리로 가져오고자 했습니다. 


### 수강생 목록 조회 전략
- 강의 목록 조회 시, 수강생 목록까지 한 번에 가져오면 강의 수 X 수강생 수만큼 데이터가 증가하여 데이터 크기를 예측할 수 없고, 심한 경우 Out Of Memory까지 발생할 수 있다고 생각했습니다.
- 이를 방지하기 위해 강의 목록 조회와 수강생 목록 조회를 분리하고, 특정 강의 선택 했을 때 목록을 조회하도록 API를 분리했습니다.


### 도메인 책임 분리 
- 서비스 계층에서 검증 로직까지 모두 처리하게 되면 코드가 복잡해져 유지보수가 어렵고, 테스트 작성 시에도 서비스의 모든 의존성을 함께 설정해야 하는 어려움이 있습니다.
- 이를 방지하기 위해 정원 초과, 상태 유효성, 취소 가능 여부 등 비즈니스 규칙 판단은 Course, Enrollment 등 도메인 객체에 위임하고, 서비스 계층은 전체 흐름 조율에 집중하는 구조로 만드려고 노력했습니다.
- 덕분에 이전 프로젝트보다 비교적 수월하게 테스트 코드를 작성할 수 있었습니다.

## 미구현 / 제약사항
### 인증/인가
- 현재 `X-User-Id` 헤더 값을 그대로 사용하여 유저를 식별하고 있습니다.
- 현재 방식은 클라이언트가 헤더 값을 직접 설정할 수 있어, 실제 인증 방식으로 사용하기에는 보안상 문제가 있습니다.
- 다만 실제 서비스에서도 컨트롤러/서비스 계층에서 결국 현재 요청 사용자의 ID를 꺼내 사용하게 되므로, 이번 과제에서는 인증 과정보다 수강 신청, 동시성 처리 흐름에 집중했습니다.

### 실제 결제 연동
- 외부 결제 연동 대신 MockPaymentGateway를 사용했습니다.
- 현재는 항상 성공하도록 처리되어 있으며, PaymentGateway 인터페이스 기반으로 실제 PG 연동 구현체를 추가할 수 있도록 분리했습니다.
- 다만, 현재 결제/취소 요청이 트랜잭션 내에서 동기로 처리되고 있어, 실제 PG사 연동 시 외부 API 응답 지연이 트랜잭션을 길게 잡아 DB 커넥션 점유 문제로 이어질 수 있습니다.
- 실제 연동 시에는 PG사 호출을 트랜잭션 밖으로 분리하거나 Outbox 패턴 등을 고려해봐야 합니다.

### Soft Delete
- BaseEntity에 deletedAt 필드를 뒀지만 사용하고 있지 않습니다.
- 이번 과제에서 삭제 기능 자체가 요구조건에 없어 적용하지 않았습니다.

### 대기열
- 수강 취소 시, 대기 순번에게 수강 신청 권한(?)을 주는 기능은 구현하지 못했습니다.
- 대기열 관리와 자동 승격 과정에서 동시성 및 상태 정합성을 함께 고려해야 한다고 판단하여 이번 범위에서는 제외했습니다.

### 동시성 테스트
- 멀티 스레드 기반 동시성 통합 테스트는 구현하지 못했습니다. 대신 비관적 락을 사용한 이유를 명확하게 작성했습니다. 

### 유저 등록 API
- UserService.create()는 구현되어 있지만 별도의 회원가입 API는 만들지 않았습니다.
- 테스트를 위해 init.sql로 유저 데이터를 추가해서 테스트를 진행했습니다.

### 결제 미완료 자동 취소
- 결제 대기 상태가 일정 시간 지속되더라도 자동 취소하는 기능을 구현하지 못했습니다.

### 객체 선정 기준
객체는 시스템 안에서 상태를 가지고 다른 객체와 협력하여 문제를 해결하는 주체라고 생각했습니다.
단순히 한 번 실행되고 끝나는 행위가 아니라, 상태를 지속적으로 유지하고 규칙과 책임을 가져야 하는 개념을 객체로 선정했습니다.

- **User** - 강사와 수강생은 사용자 정보와 역할을 가지고 서비스를 이용하기 때문
- **Course** - 정원, 신청 기간, 가격 등의 상태를 지속적으로 관리하고, 신청 가능 여부와 정원 초과 여부를 판단해야 하기 때문
- **Enrollment** - 수강생의 강의 신청 진행 상태를 기록하고, 결제 대기/수강 확정/취소 등의 상태 변화를 관리해야 하기 때문
- **Payment** - 결제 시도/성공/실패/취소 상태를 관리하고, 결제 완료 여부가 수강 확정 조건이 되어야 하기 때문

### 관계
- User(강사) 1 : N Course
- User(수강생) N : M Course (Enrollment를 통한 간접 참조)
- User 1 : N Enrollment
- Course 1 : N Enrollment
- User 1 : N Payment
- Enrollment 1 : 1 Payment
